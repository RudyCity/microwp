# Private PHP-WASM ↔ Worker D1 SQL protocol (prototype, v1)

**Experimental; not connected to any HTTP route or production WordPress wpdb layer.** In particular, no changes
are made to `src/index-durable.ts` or `src/php/native.ts`. The only intended caller
is a future *trusted in-process PHP-WASM host callback*. Integration must separately
authenticate/authorize that private callback and guarantee correct site context.

## Wire envelope

PHP sends UTF-8 JSON (<= 16 KiB) through a trusted internal string exchange;
Worker responds with JSON (<= 64 KiB). `version` is always `1`, `id` is
a 1–64 character ASCII correlation ID and is echoed only after validation.

SELECT example:

```json
{"version":1,"id":"req_123","op":"select","table":"posts","columns":["id","title"],"where":[{"column":"slug","value":"hello"}],"orderBy":{"column":"id","direction":"asc"},"limit":25,"offset":0}
```

Bounded SELECT `IN` example (experimental, still private):

```json
{"version":1,"id":"req_123_in","op":"select","table":"wp_options","columns":["option_name","option_value"],"whereIn":{"column":"autoload","values":["yes","on","auto-on","auto"]},"orderBy":{"column":"option_name","direction":"asc"},"limit":50,"offset":0}
```

The optional `whereIn` permits one 1–8-element, scalar-only, non-null, distinct value list. It is **SELECT-only**, cannot duplicate an equality predicate or target a host-owned tenant scope, and its column must exist in the trusted table policy's `filter` allowlist. All values are SQL `?` bindings; no raw SQL fragments or `IN` source expressions are accepted. The maximum possible v1 SELECT binding count is 19 (8 equality predicates + 8 IN values + scope + LIMIT/OFFSET), under the cap of 20.

INSERT example:

```json
{"version":1,"id":"req_124","op":"insert","table":"posts","values":{"slug":"hello","title":"Hello"}}
```

Experimental UPDATE (only after an opaque, host-owned UPDATE capability and unique-key policy are approved):

```json
{"version":1,"id":"req_125","op":"update","table":"posts","values":{"title":"Revised"},"where":[{"column":"id","value":3}]}
```

Experimental DELETE (requires a distinct DELETE capability):

```json
{"version":1,"id":"req_126","op":"delete","table":"posts","where":[{"column":"id","value":3}]}
```

Responses:

```json
{"version":1,"id":"req_123","ok":true,"op":"select","rows":[{"id":1,"title":"Hello"}]}
{"version":1,"id":"req_124","ok":true,"op":"insert","changes":1}
{"version":1,"id":"req_123","ok":false,"error":"NOT_ALLOWED"}
```

## Safety contract

- **No raw SQL** is accepted. Structured SELECT/INSERT plus strictly bounded,
  separately authorized experimental UPDATE/DELETE. No DDL, joins, expressions,
  OR predicates, multi-statement SQL or dynamic SQL snippets. UPDATE/DELETE
  require WHERE with a non-null equality predicate for an explicitly trusted
  unique/primary-key identity column. Scope-only/bulk mutations are refused.
- Worker validates every field, exact object keys, identifier syntax, operations,
  numeric bounds, parameter count, and result size *before/after* D1 access.
- D1 SQL is *generated by Worker* with quoted, policy-approved identifiers and
  `?` bindings for every scalar value, including LIMIT and OFFSET.
- Table policy must be configured from trusted Worker code, **never from PHP**;
  absent tables and unspecified operations are denied. Restrict select, insert,
  filter and order columns independently. UPDATE and DELETE are disabled by
  default and need distinct write-operation capabilities in the in-process
  runtime adapter. INSERT requires its own key as well.
- Optional `scope: { column, value }` is **server-owned**: it is appended to
  SELECT/UPDATE/DELETE and injected into each INSERT. Client cannot supply the same column to
  overwrite the scope. This is a minimum site/tenant isolation guard, not a
  substitute for per-request authorization.
- Limits: input 16 KiB, output 64 KiB, scalar UTF-8 2 KiB, 16 columns, 8 equality WHERE
  predicates, one 1–8-value IN predicate, 20 bindings, SELECT 1–50 rows, OFFSET 0–1000.
- D1 errors are returned as generic codes; no SQL/parameter contents are logged
  or echoed. PHP throws a generic exception on errors.
- `worker.ts` offers only a DI function, not a `fetch` handler. **Never mount
  it on public routes** or let a public request choose the policy.

## Non-production example

```ts
import { handleD1ProtocolMessage } from "./src/php/d1-protocol";
const policy = {
  tables: {
    posts: {
      select: ["id", "title"], insert: ["title", "slug"],
      filter: ["slug"], order: ["id"],
      scope: { column: "site_id", value: "site:alpha" }
    }
  }
} as const;

// Only from a private, authenticated, in-process PHP-WASM callback:
const reply = await handleD1ProtocolMessage(internalMessage, env.DB!, policy);
```

The PHP helper `client.php` needs a private callable `fn(string): string`
provided by a **future** WASM bridge; it does not implement that transport.
SQL grammar is intentionally much smaller than WordPress/SQLite wpdb needs.
No live Cloudflare DB or schema is modified by this prototype.

## Experimental single-row mutation caveats (2026-11-06)

The host may configure `update: ["title"]`, `delete: true`, `identityColumn: "id"`, and `filter: ["id"]` **only after schema verification** confirms the identity column is unique. The `createD1RuntimeAdapter` caller must hold the original server-owned `callerKey` and a separate identity-matched capability for each INSERT/UPDATE/DELETE. The raw host handler requires a second explicit destructive-operation argument for UPDATE/DELETE. These keys are in-memory host objects, not request JSON, query parameters or user PHP values.

The returned `changes <= 1` check is only a **post-execution diagnostic**, not an atomic rollback. If the trusted schema does not actually enforce uniqueness, an invalid mutation could modify more than one row before detection. This requires a verified PRIMARY KEY/UNIQUE constraint and transaction-level tests before activation. This code does not implement full WordPress `wpdb` semantics, transactions, MySQL compatibility, plugin queries, automated migration or replay-safe mutation IDs. The existing PHP `src/php/d1-wpdb/db.php` is still strictly read-only and is not installed. Production remains **NO-GO**.

See [experimental mutation safety report](../../docs/reports/2026-11-06-microwp-d1-experimental-mutation-safety.md).

## Pinned WordPress autoload query prototype (2026-11-06)

The private query translator at [options-autoload.ts](../d1-wpdb-conformance/options-autoload.ts) recognizes the concrete autoload query in the pinned `wp-includes/option.php`, restricted to the four official autoload values and subsets. It produces deterministic bounded pages of 50 D1 rows and requires a trusted site-owned table mapping, with all SQL values bound. The prototype **cannot be used as a complete WordPress alloptions loader** until full pagination, snapshot consistency, fallback semantics, and oversized result behavior are verified. No production WordPress driver is installed. See [autoload conformance report](../../../docs/reports/2026-11-06-microwp-d1-autoload-options-conformance.md).

## Verified autoload paging (non-atomic prototype)

The private WordPress `wp_load_alloptions()` reader at [options-complete.ts](../d1-wpdb-conformance/options-complete.ts) refuses incomplete results rather than returning a truncated options cache. It performs two bounded page reads with an extra overflow probe if the last permitted data page is full and checks data equality between passes. A passing result is **not** proof of a transactionally consistent snapshot. No public endpoint, production WordPress database integration, or remote D1 migration is enabled. See [complete-read proof](../../../docs/reports/2026-11-06-microwp-d1-autoload-complete-read-proof.md).
